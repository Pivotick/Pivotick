Rim badges — declared potential only

A badge says the data source declared there is more here, before any provider has been called. Queried counts never reach the rim — otherwise a number would materialise on one node the moment it is selected and the canvas would stop being consistent (D12). Nothing on the rim ever changes because of a selection or an open menu.

B1one pivot declares
A pill on the NE corner, in var(--pvt-badge-color). Past three characters the library renders 99+, so large counts are abbreviated by hand — 2.1k, not 2,143.
B2several declare
Four corners, so three badges and the library's own +n overflow. The collapse is automatic — BadgeDrawer already hands out corners clockwise from NE and spends the last one on +n.
B2′on a container
A node with children reserves both east corners for the expand affordance, whatever its state — so exactly two are left, and a second pivot already forces +3. This bites hardest on precisely the container nodes that matter most.
B3cleared
setPotential(id, 0) removes the badge outright. There is no "0" state on the rim — a zero badge would advertise the absence of data, which is noise.

C13 The overflow badge concatenates the hidden badges' titles one per line, so every line has to stand alone. A fragment like "and 40 more" becomes gibberish when stacked.

C11 The count, not a glyph. The number is the content of declared potential. A glyph says only "something", which the analyst then has to open a menu to resolve — which is the cost the badge exists to avoid.
C12 Clicking a badge opens the pivot menu, scoped to that pivot. NodeBadge.onClick exists and consumes the click, so the node is not also selected by accident — meaning the shortcut can select the node and open the menu deliberately, as one gesture.

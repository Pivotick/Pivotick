Where the pivot menu lives

Round 1's three placements are ruled out below. These two are new: D makes Pivot a rail mode of its own, with its own tools and options; E puts the menu in the dock, beside the results it produces. The states and every word are fixed in pivot-enrichment-ui-states.md, so these differ in placement only.

DPivot as its own rail moderecommended
+The mode boundary is the intent boundary. Entering Pivot mode fires summarize; leaving it stops every call. D11 asks for exactly this and gets it for free.
+Full canvas height, and completely independent of how many properties a node has.
+It has tools: Pick origin / Lasso origin make the 50-node bulk flow first-class instead of an afterthought.
+Mode-scoped canvas options — "dim nodes with no pivots" — that no other placement can offer.
−Still a column: 4 facets with counts want more than the panel's 216px, so this asks for 300px.
−A full-height panel pushes the legend off the canvas's left edge.
EThe menu in the dockstrong alternate
+1,260px of width instead of a column. All four facets are visible at once, side by side, with nothing scrolled or squeezed.
+The whole pipeline in one region: choose the pivot, narrow it, fetch, and triage — as adjacent tabs.
+Zero new chrome. It is a DockTab, which already exists.
−Needs the dock open — 332px, 35% of the viewport — to do anything at all.
−The dock is framed today as read-only reflection ("the table reflects and selects, and never changes the graph"). This makes it an action surface.
−No canvas participation whatever, and the pivot list column half-duplicates the tab strip beside it.

Ruled out in round 1

A Pivot section inside the Select tool panel. Mode-scoped, so switching to Create to draw one edge discards a narrowing session — and it put an analytic surface inside a pointer mode. D is this idea done properly: its own mode, so the switch is deliberate and the state is remembered.
B Popover anchored to the selection. Overlaps the dock by 168px at an ordinary anchor, needs re-anchoring on every pan and zoom, competes with the context menu for the same gesture, and has no honest anchor for 50 selected nodes.
C A Pivots tab in the selection sidebar. Killed by measurement: property rows are 61px and the sidebar scrolls as one column, so the tab row sits at y=402 with four properties and falls below the fold at thirteen. MISP attributes routinely carry more, so the pivot surface would live under a screenful of scrolling on exactly the nodes that matter.

Why a pointer mode, not a flyout

View and Physics are kind: 'flyout' — a settings overlay, 252px, and no tools at all. A kind: 'pointer' mode instead gets tools as a function re-read on every render (so the pivot list follows the selection), a render() slot for anything the rows cannot express (the narrowing controls), and onEnter/onExit — which is where summarize starts and stops.

The library's own doc comment already names this door:

"A mode registered onto the mode rail — the door an integrator builds their own Explore or Enrich mode through."

Recommendation — Variant D

D is the only placement whose open/closed boundary is a real thing the user does rather than a thing we invent. Entering Pivot mode is unambiguous intent, leaving it is unambiguous disinterest, and D11's "a closed menu costs zero backend calls" becomes a property of the mode rather than a rule to enforce. Nothing else on offer has that. It also makes the bulk flow — pick or lasso an origin set — a first-class gesture rather than something borrowed from Select mode.

E is genuinely better at one thing, and it is not a small thing: narrowing has room to breathe. If four facets in a 300px column turn out to be the pinch point once real providers are wired, E is the fallback that already has the width — and D's own results already land in the dock, so moving the menu there later is not a rewrite.

What D changes, and what it still needs

  • It reverses a PRD decision. §12 and D25 say the library ships no Enrich rail mode and the consumer builds it. A built-in Pivot mode is the opposite; the brief's §5 hard rule needs rewriting with it.
  • A 300px tool panel — the panel is a fixed 216px today, so this needs a per-mode width.
  • The legend moves while Pivot mode is open, or the panel scrolls instead of growing. Drawn here as the legend moving.
  • Still outstanding from round 1: the actionable toast, DockTabHandle.setLabel(), and dark tokens for the refusal amber and the success-toast green.

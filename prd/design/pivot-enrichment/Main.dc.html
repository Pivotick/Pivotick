Where the pivot menu lives

Three placements, one flow: select the AIL paste node → open the menu → ~2,143 against a cap of 2,000 → refusal → tick URLs → ~210, under cap → fetch → triage → ingest 12. The states and every word are fixed elsewhere (pivot-enrichment-ui-states.md), so these three differ in placement only — which is the actual decision.

+340px hosts the existing 332px control vocabulary unchanged, and 50 selected nodes need no special case.

One flat entry, not a Pivot ▸ submenu: MenuActionItemOptions has no children (GraphUI.ts:706). It opens the winning surface. visible takes a predicate, so it hides itself when nothing applies — free appliesTo.

Recommendation — Variant C

Variant B is the one that looks right and the measurements kill: it collides with the dock, needs re-anchoring machinery on every pan, and has no answer for a bulk selection. Variant A is defensible but buys its room by putting an analytic surface inside a pointer-mode panel, where a stray click on Create discards the narrowing.

Variant C wins on the thing that is easy to miss: the PRD's own behaviour is already tab-shaped. summarize fires when the menu opens, re-runs while it stays open as the selection changes, and costs nothing while closed (D11) — which is precisely the lifecycle of a sidebar tab, for free, with no new chrome and no new open/close concept. It also fits the existing control vocabulary at its existing width, and treats 50 selected nodes the same way it treats one.

Three things this design needs that the library does not have yet

  • An actionable toast. Not just a button: today's dies on a hard 4s timer with no handle, which is less time than it takes to read "Ingested 12 nodes, 14 edges". Without it, auto-ingest pivots have no undo surface at all.
  • A live dock-tab label, or the count stays in the pane header. DockTabHandle has no setLabel.
  • Two dark tokens — the refusal amber and the success-toast green have no dark counterpart in _variables.scss.

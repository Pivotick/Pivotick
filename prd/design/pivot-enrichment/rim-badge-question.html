Pivot enrichment · at-scale finding 7

What should a node's rim say?

One question, built from nothing. Every rim below is drawn by the same corner rules the renderer uses, so none of these pictures flatter the argument.

01

A badge is a provider saying “there's more here”

A provider can tell the graph how much it holds on a node without fetching any of it:

node.setPotential('ail-correlations', 2143)

The graph draws that number on the node's corner. Click it and the Pivot panel opens on that provider. That is the whole feature as it stands today.

02

The number belongs to one named provider

setPotential takes a provider id. Two providers with something to say put two separate numbers on the node, each opening its own provider when clicked. A plain node has four corners, so four of them fit.

03

A node with children only has two corners

The expand control owns both right-hand corners — it sits top-right while the node is closed and bottom-right once it is open, so both stay reserved either way. Two corners are left over.

Declare four providers on such a node and you get one number and a grey +3. That +3 cannot be clicked; it only lists what is hidden in its tooltip.

04

Then the real service turned up

misp-modules registers 118 providers, and 51 of them apply to a single ip-src. There is no arrangement of fifty-one numbers on four corners.

So the misp-modules page does not use badges at all. It invents one fake provider whose only job is to own a badge, and hangs a number off that. That workaround is finding 7.

Settled

What the one number counts

Two different numbers were wanted here, and you chose to ship both and let the consumer pick between them. Nothing below re-opens that.

How many providers apply

An AS node shows 2, an ip-src shows 51. The graph works this out itself by asking each pivot whether it applies.

nobody declares anything

How much is out there

One total across every provider at once — roughly 2,199 things waiting. Only the backend knows this, so the consumer says it.

consumer declares it

Either way it is one badge that belongs to no single provider — which is exactly the thing that has no way to exist today.

Open

When a node carries both kinds at once

This is the question I asked badly. Once the number above ships, a node can wear two kinds of badge: the per-provider ones from step 02, and the single one that belongs to no provider. The corners did not become more numerous. So which kind gets one?

All three rims below are the same node with the same declarations: AIL 2,143 · Passive DNS 44 · VirusTotal 12 · Shodan 3, plus a declared total of ~2,202. It has children, so it has two corners.

Option A

The total goes first

The total takes a corner. The per-provider numbers queue behind it and spill into the +n.

Cost: per-provider badges get crowded out — but only on nodes where a total was declared.

Option B

Only ever the total

The graph adds the per-provider numbers together and shows one badge, always. The simplest possible rim.

Cost: two providers on a plain node used to give a click straight into AIL. Now nothing does.

Option C

The total takes what's left

Per-provider badges keep their corners; the total appears only if a corner happens to be spare.

Cost: on a node with children it never appears at all — the exact node type MISP produces most.

I'd take A

It is the only one where a consumer who declares nothing new keeps exactly today's rim, and the only one whose cost is something they opted into: if a total is pushing providers into the +n, it is because they declared a total and said that is the number that matters.

B throws away a working feature everywhere in order to fix a problem that only appears at 118 providers. C fixes the finding everywhere except the case that raised it.

Finding 6 is already settled and nothing here depends on it: appliesTo may now return the nodes it applies to instead of true or false, so a pivot can cover 3 of the 5 nodes you selected instead of bowing out entirely.
